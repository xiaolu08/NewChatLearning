# ChatLearning AstrBot 移植的问题与机会

## 结论在前

原版的核心价值不是“聊天记录知识库”这一泛称，而是一套无需生成式模型的群聊行为学习器：把连续消息归纳成问答关系，再按频次、过滤规则和概率进行拟人化回复。AstrBot 能解决接入层老化问题，并提供现代插件配置与生命周期；真正的难点在于完整还原旧行为、处理多媒体与旧词库、避免阻塞事件循环，以及建立今天所需的隐私和安全边界。

## 正文

### 用户问题

- Mirai HTTP 依赖和旧 QQ 登录链路已不适合作为长期平台基础。
- 原版代码是独立常驻程序，线程、轮询和磁盘 pickle 与 AstrBot 的异步插件模型不匹配。
- README 中的功能跨度很大，简单移植“学习和回复”会遗漏管理、过滤、标签、合并、删除和定时任务等用户实际依赖。
- 旧 `.cl` 文件使用 pickle，直接加载外部文件可能执行恶意代码，不能在插件主进程中无条件导入。
- 用户提供的三份共享词库虽未发现危险 pickle opcode，但包含约 30 万答案和大量旧媒体引用，兼容测试不能只覆盖文本。
- 群聊内容长期保存涉及知情、删除、备份、泄露和群间串库风险，需要比旧项目更明确的默认策略。

### 核心机会

- 将学习算法与平台适配解耦，先保证 QQ/OneBot 完整体验，同时保留未来适配其他 AstrBot 平台的可能。
- 用 SQLite 事务和版本化 schema 替代多个 pickle 文件，提高并发、查询、备份和迁移可靠性。
- 用 AstrBot 配置 schema 暴露常用设置，用聊天命令覆盖日常管理，减少手改配置文件。
- 保留零 Token 的算法内核，并用离线可测试的匹配器支持精确、正则和传统文本相似度。
- 建立可重复的“原版行为夹具”，让完整移植可以逐项验收，而不是依赖主观感觉。

### 风险与反例

- “功能全保留”不等于保留原版所有内部缺陷；例如 `eval`、不可信 pickle、同步睡眠和裸异常捕获必须重构。
- OneBot 实现之间对语音、闪照、转发和卡片的支持不同，某些能力只能声明适配范围而不能保证跨平台一致。
- 群聊学习天然可能复述隐私、冒犯内容或错误信息；过滤只是缓解手段，不能等同于内容安全保证。
- 本地相似度全表扫描在大词库上可能造成明显 CPU 和响应延迟，需要索引、缓存或候选召回机制。
- 若插件命中后仍进入 AstrBot 的 LLM 流程，可能出现双重回复并间接产生 Token，必须明确事件终止语义。

### 最小验证建议

1. 从原版构造文本、图片、@、引用、过滤、权重和时间间隔的行为样本。
2. 制作不连接 QQ 的领域层原型，验证相邻消息学习与加权回复结果。
3. 制作最小 AstrBot 插件探针，验证 OneBot 群消息接收、消息链回发、命令拦截和停止后续 LLM 流程。
4. 对 10 万至 100 万问答规模做 SQLite 与相似度检索基准。
5. 在隔离子进程中验证旧 pickle 迁移方案，禁止主插件直接加载未知文件。
